# Integrate KEEP and ME6-Opti with separate boundary evidence

On 2026-11-10 the user chose to plan both sixth-order explicit and compact
original KEEP, together with ME6-Opti CPU/GPU integration and stretched-grid,
static-curvilinear and physical-wall extensions. The donor code supplies an
explicit KEEP core and a periodic uniform-grid ME6 implementation, not a
finished coupled boundary method. Their existing guards and low-order wall
connections are not the specification for the new solver.

Original arithmetic-average KEEP is the selected baseline. KEEP-PE, revised
entropy-preserving variants, AIR5 and new shock-capturing coupling are deferred.
Convection and viscosity remain independently selected, with existing defaults
unchanged. Current derivative choices are reused rather than adding duplicate
order or explicit/compact controls. CPU and GPU use the same mathematical
definitions, while keeping host and device implementations separated.

The user prioritized compatible stability over sixth-order local accuracy at
every boundary node. Lower local boundary order may be researched, with local
truncation, global convergence and physical-quantity errors reported separately.
This is specific to the new KEEP/ME6 plan and does not relax ADR-0054's existing
HB requirements. No particular SBP/SAT operator or penalty is approved yet.

Discrete balances and local/frozen-system analyses accompany representative
nonlinear verification; no universal nonlinear entropy-stability theorem is
promised. Same-algorithm FP64 CPU/GPU frozen-state comparisons use the approved
scaled maximum difference of 2e-10. Different methods and long nonlinear
trajectories are not required to match pointwise. Numerical validation disables
crashfix; the existing optional operational repair remains separate evidence.

All three non-shock farfield modes are in scope, each retaining its own physical
meaning. Exact restart must identify the effective algorithms; explicit non-exact
switching is allowed with derived-state rebuilding and a new statistical window.
Existing checkpoint machinery is reused rather than adding flow-field copies.

Following the brainstorming review, the user chose option A: retain one master
plan and the full agreed scope, with independently deliverable periodic explicit
KEEP, compact KEEP and ME6 stages. KP0 must resolve configuration ownership,
discrete balance definitions and effective numerical identities. Filter selection
and geometry derivatives cannot remain incidental consequences of a shared
compact switch. Identity recording must also cover fully explicit combinations,
with short restart checks attached to each operator rather than deferred to final
integration.

A preliminary KP0-A analysis exposes boundary and metric constraints before
device interfaces and geometric extensions are finalized. It does not select an
unreviewed closure or require a universal stability theorem. The geometry stage
checks metrics generated by the actual initialization path. ME6 component checks
include its straight and mixed wavenumber responses and complete viscous-symbol
behavior, not only Taylor order or CPU/GPU parity. Discrete budgets state their
quadrature, unique-node ownership, pressure-work exchange and separate temporal
and filtering contributions.

Formal delivery targets FP64 and representative numerical/stability evidence.
FP32 validation, performance campaigns and production turbulent-DNS statistical
acceptance are deferred. These decisions authorize planning only; implementation,
new mathematical candidates and remote jobs retain their separate review points.
